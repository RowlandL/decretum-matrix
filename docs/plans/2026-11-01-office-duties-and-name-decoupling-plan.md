日期：2026-11-01。状态：**PLANNED_UNVERIFIED**。本次仅修改计划，不修改现用官署配置、运行代码、安装或版本，不发布。

关联：[版本总纲](2026-10-03-decretum-matrix-remediation-plan.md)、[统一决策与原生化增补](2026-11-01-memory-decision-gateway-roadmap.md)、[考据与现状说明](../research/2026-11-01-memory-decision-gateway-sources.md#8-官署职责史实与名称解耦依据)。

## 1. 最新需求与取舍

- 用户最初给出的门下、中书、尚书和CEO/COO例子是意图说明，不作为完整历史职责或固定职位映射。
- **职责来源以史实为准，产品实现必须适应现代智能体。** 主要参考唐代三省六部的制度分工，明确时期差异；不混用唐、宋、明、清作为一个恒定制度。
- 用历史的拟定、审议封驳、行政统筹与六部专业分工组织智能体工作，不复刻古代官阶、仪礼、文书流转次数或常设人员规模。
- 职责、工作方式、身份与显示名称分离；可用古代官名、CEO/COO、团队称呼或人名显示，改名不改变职责体系。
- 中书的现代重要交付之一是模型可理解的结构化需求/提示词/计划。结构可按任务扩展，但必须有统一语义骨架，不将“写提示词”冒充全部历史职责。
- 三省六部是本项目选定的组织设计来源。其是否适合具体AI任务，用成功率、纠错、成本、交互与恢复数据判断，不从历史用途推导普遍优于所有管理方式。

## 2. 历史职责基线：唐制为主

下表是历史概括，不是现有软件能力声明。三省的政令分工可由唐代授官文书研究印证；六部隶属及职掌须结合时期理解。[故宫学刊：授官文书研究，第34–35页](https://www.dpm.org.cn/Uploads/File/2020/04/10/u5e90203ee185a.pdf#page=6)、[故宫博物院：六部](https://www.dpm.org.cn/court/system/236422.html)

| 机构 | 历史职责概括 | 不能混同的职责 |
| --- | --- | --- |
| 中书省 | 参与政务决策，草拟、形成诏令文书 | 不等于所有专业行政的执行机关 |
| 门下省 | 审议政令，审核、封驳不当文书，参与中枢政务 | 不只是文字校对，也不等于包揽司法监察 |
| 尚书省 | 中央行政统筹，承接政令、分付六部及所属诸司实施 | 不只是收集总结报告 |
| 吏部 | 官员铨选、任用升黜、考课等 | 考试取士与铨授官职不是同一环节 |
| 户部 | 户籍、土地、赋税、钱粮与财政 | 不等于任意事项的最终授权者 |
| 礼部 | 礼仪祭祀、宾客及特定时期的贡举等相关事务 | 不是古代通用写作部门；贡举归属有变化 |
| 兵部 | 武官选授及军政、兵马军械等军事行政 | 不等于恒常独占全国作战指挥权 |
| 刑部 | 刑法、刑狱行政与案件复核等 | 不独占大理寺的审判或御史台的监察 |
| 工部 | 工程营造、水利、屯田、工匠等事务 | 不因负责工程就兼有政令拟定和最终审查权 |

上述三省流转是选取的常态政令范式，不宣称唐代每件文书都经过完全相同程序。唐代内部亦有制度演变；例如常举由吏部考功转归礼部，不能写成整个唐代始终不变。后世六部隶属亦有变化；明初改为直接对皇帝负责，不作为本项目尚书统筹六部的历史依据。[故宫六部词条](https://www.dpm.org.cn/lemmas/240651.html)、[礼部贡举研究](https://tslc.cbpt.cnki.net/portal/journal/portal/client/paper/12364e05848b21fb5a13e812489f063d)

太子、史馆、御史台和朝会不列为三省六部组成。项目中的用户代理、史馆记忆、监察诊断与早朝简报保留为现有辅助职能，其软件边界单独说明。

## 3. 现代智能体职责合同

本节是**现代适应化设计**，不是史实复刻。复用现有role_key、profile/dossier、assignment与证据链，为各职责补齐输入、决策范围、交付物、交接对象和停止/升级条件。

| 职能槽位 | 现代主责 | 主要交付与协作边界 |
| --- | --- | --- |
| 用户入口 / 太子 | 接收意图、明确授权与结果边界、上行澄清、汇合三省意见并对用户回奏 | 绑定当前旨意与结果章程；不代中书完成全部拆解，不直接指挥六部 |
| 中书 | 分析需求与依赖、研究方案、形成计划/诏令/结构化任务提示、拟定验收标准；归并经审议的修改 | 可执行的需求与任务包、版本化计划、必要文书；规划不能直接当作真实派遣或完成证据 |
| 门下 | 审查需求覆盖、方案、授权边界、风险、证据与结果；接受或以具体问题封驳 | 有理由的审查结论、修改条件和接受范围；记忆写入建议在当前授权内由门下批准或拒绝；不悄悄替写方案后自行批准 |
| 尚书 | 评估可分派性，统筹六部、执行依赖/并发/资源安排、差遣与跟进、阻塞升级、结果统合 | 六部工作单、执行状态与证据化汇总；可细化执行步骤，重大目标/方案变化返回中书与门下 |
| 吏部 | 维护官署/智能体/工具/技能能力信息，评估适配、任用及表现，提出能力缺口建议 | 候选及依据交尚书；身份任命、安装、模型使用仍遵循现有授权 |
| 户部 | 计算资源、Token/费用/时限预算、容量、依赖与环境/资产盘点 | 可执行的资源约束与实际消耗；预算优化不能替代权限判断 |
| 礼部 | 交互与交付规范、术语/引用/格式、教育和沟通材料；承接获派的文书制作 | 中书负责计划/诏令语义和结构，礼部提供专业表达与交付加工；各部仍对自身事实负责 |
| 兵部 | 执行力量准备、行动资源与任务动员的专业建议，复杂应急/迁移行动的协调方案 | 尚书统筹下的专业工作包；不独占所有派遣或实际工具操作，不把“军事”映射成无限攻击权限 |
| 刑部 | 规则、安全、隐私、风险及验证/回滚的专业审查 | 提供可核查的风险与合规意见；门下负责综合审议，不将二者做成重复的全量审批链 |
| 工部 | 实现、原型、构建、测试/QA、工程工具和获授权的应用操作 | 返回实际产物、命令/工具证据与失败范围；不自行扩大需求或批准自身成果 |
| 史馆（辅助） | 实录、来源/证据、记忆候选整理、已批准裁定的记录与派生检索 | 仅在当前授权内执行并记录已批准决定，不自行批准记忆写入；记忆不取得任务执行权，不建立新官署指挥链 |
| 监察（辅助） | 有界诊断、制度偏离和运行异常证据上报 | 当前范围按既有profile核对；通用监察扩大另设计，不能自任执行/恢复/杀进程权 |
| 早朝（工作方式） | 状态简报、复盘、待决问题与跨职责信息同步 | 按需报告或会商，不为所有任务强制开会，不成为第二指挥中心 |

现代职责冲突按“谁拥有语义、谁实施、谁审查、谁记录”解决。一个任务不必调用六部全员；按能力和实际依赖启用职责。路由可用Laya或其他决策器建议，但由稳定职能合同和既有准入执行，不能仅凭显示名称分配权限。

## 4. 适应智能体的工作方式

### 4.1 规划、审议与执行协作

1. 用户入口绑定结果、范围和授权；中书把自然语言转换为可执行的结构化任务。
2. 门下按风险审议：小任务采用轻量检查，复杂或高影响任务独立复核；反馈聚焦实质问题，不为措辞反复空转。
3. 尚书评估分派性与执行安排。中书、门下、尚书可以在拟定期间会商，尽早发现不可执行项；不把历史政事堂变成强制的多轮会议。
4. 任务经合法上级分派到有关六部，再到该部自己的有界工坊；无关部不启动。
5. 尚书将产物、失败、尚缺证据与下一步统合；门下按接受范围复核，史馆按既有策略记录，用户入口回奏。

串行、并行、复用和换新是执行策略，不由古代官名、CEO/COO标签或人数决定。serial_inline可保留责任分工，记录实际承载方式；若明确要求独立审查，不能靠同一实例换名伪造独立性。风险升级或重大范围变化返回原责任方；不存在由网关或模型自行扩权的捷径。

### 4.2 统一结构，按任务变化

复用既有profile的duty/can_do/cannot_do/procedure/report_contract，以及当前assignment/P00。**统一的是语义骨架，不是每次都输出同一长篇JSON。**

| 稳定语义槽位 | 必须表达的内容 |
| --- | --- |
| 目标与意图 | 要解决的问题、期望结果、当前用户约束及非目标 |
| 输入与来源 | 必要材料、证据指针、已知事实和待验证假设，注明信任边界 |
| 职责与边界 | 所属职能、直接上级、允许读写、禁止动作和已有授权 |
| 工作与依赖 | 本次具体问题/步骤、前置、可并行部分和必要决策点 |
| 交付与验收 | 预期产物、格式要求、成功/失败判据及证据 |
| 交接与恢复 | 接收方、状态、未决项、停止/升级及回退条件 |

按任务增加扩展：工程任务的接口/兼容/验证；研究任务的问题/来源标准/不确定性；文书任务的受众/结构/表达；运维任务的复现/影响/恢复；审查任务的范围/发现/接受理由。无关扩展不生成，不填大量空字段。短任务用简短业务语言体现相同槽位即可。

核心边界不能由扩展覆盖；缺少必要信息才回到责任方澄清。文书、模型提示和宿主消息从同一有效任务投影，避免分别维护含义不一致的多份指令；沿既有版本、P00和预算，不新增平行胶囊或强制重复预载。

### 4.3 与决策、记忆和缓存协同

- Laya/宿主模型按实际职责和合法候选选择角色；选择策略、判断质量与宿主回退沿前一份增补计划。
- 门下审查与尚书统合使用真实证据；不能将模型“认可”、角色名、checker PASS或spawn成功当成履职完成。
- 中书按任务组织提示内容，保持既有上下文前缀；职责变化、补充材料和记忆仅以合法新消息追加。
- 仅更改显示名不逐轮重写system/tools或全部历史。职责合同发生实质变化时按现有计划修订/新context epoch处理，明确成本与兼容，不能为缓存保留已撤销权限。

## 5. 职责、身份与名称解耦

### 5.1 复用现有身份设计

已有[身份包/DLC计划](2026-07-16-decretum-matrix-office-identity-pack-dlc-and-scope-plan.md)仍为PLAN_ONLY。其中skin只改展示，profile/dossier承载职责，替换仍保留治理职责。本次续接这一设计，不将其宣称为已实现，不另建名称表、权限账册或第二resolver。

| 层 | 保持或允许变化 | 消费规则 |
| --- | --- | --- |
| 职能与责任 | 稳定role_key、职责合同及版本、直属关系、准入与审查责任 | 路由、派遣、复核和证据使用结构化绑定 |
| 实例与工作单 | assignment_id、实际host实例、会话与任务绑定 | 同名不等于同实例，换名不等于新角色 |
| 能力与工作方式 | 可用工具/技能、任务扩展、串并行与复用策略 | 按任务/风险/能力选择，不从称谓推断 |
| 展示与风格 | display_name、称谓、头像/图标、受控语气和排版 | 可用古代官名、CEO/COO或人名；不授予权限，不改变流程 |

不规定CEO必须等于太子、COO必须等于尚书。项目显式把一个显示名绑定到所选职能；同一称呼可在不同项目有不同绑定，必须隔离。一个人或宿主可承载多个职责，但工作单要标实际职能，审查独立性也要如实披露。

### 5.2 现有命名约束的迁移

现行[官署身份绑定](../../references/sections/court-office-name-profile-skill-binding.md)仍使用canonical token和前缀，同时已将sidebar/title限定为展示。未来迁移沿其真实assignment、准入、capture和host实例绑定，将显示字段与校验身份的消费者分开。

- 技术命名兼容可保留canonical前缀，但不得仅由名称字符串推断角色、权限或直属关系。任意显示名不需冒充一个新的role_key。
- 任意host显示名的支持需实际carrier验证；不能只改UI就声称跨宿主完全解耦。
- 重名、别名冲突、缺失/未知职能不能猜测绑定；给出明确恢复路径。姓名中含CEO、门下或管理员等文本也不产生权限。
- skin不可更改can_do/cannot_do、证据要求、直接上级和停止条件；实质职责变更属于受控augmentation/replacement，不作为改名偷偷生效。
- 缺包、配置不可用或旧版本不能识别时回退内置显示和现有职责，保留原绑定并说明降级原因。
- 审计保留role_key、合同/名称配置版本、assignment及当时显示快照；历史记录不随当前改名重写。

## 7. 验收、清理与证据

- [ ] 历史职责、时代差异、现代映射三者分栏可追溯；不把现代提示词/Token/模型职责标成古制史实。
- [ ] 三省与六部主责、输入输出、禁止项、上级及交接清楚；辅助角色不冒充三省六部组成。
- [ ] 同职能换古名/企业名/人名，职责、派遣边、接受结果与能力准入不变；未授权的实质职责修改不被skin接受。
- [ ] 研究/工程/文书/运维任务共用语义骨架，扩展随任务变化，无多余空字段、重复胶囊或全员常驻要求。
- [ ] serial_inline与真实独立审查分别留证；同实例换名不能伪造独立审查，汇总不能替代门下接受。
- [ ] 按职责路由、本地模型不可用时宿主接续、名称配置失败时内置回退均可回放；旧任务和真实host身份不因改名失联。
- [ ] 新材料/名称变化遵循追加式上下文与epoch规则，观测TTFT、Token、工具轮次和审查返工，避免新增纯礼仪开销。
- [ ] 后续同步department-map、profile/dossier及host投影时，清理已被用户禁用的Superpowers能力引用，并核对监察等辅助职责；本次只列计划，不修改现用技能或角色文件。
- [ ] 对照核验总纲、9份后续版本增补及旧身份包计划的适用边界；所有新增能力仍标PLANNED_UNVERIFIED。
