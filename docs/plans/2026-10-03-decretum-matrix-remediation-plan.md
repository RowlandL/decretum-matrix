### 4.1 F24 — fast-open 实例编号与生命周期不兼容（P2）

- 问题：`court open --fast` 默认产物生成 `role#<12hex>`（真实样例 `zhongshu#4defa014347b`），消费者只接受 `role#四位非零数字` 或既有 `role-...`；admission 只查非空，未在 spawn 前拦截。
- 位置：`scripts/commands/court_open_fastpath.py:937`（生产）；`scripts/court_runtime.py:1589`（消费）。
- 修复：fast-open 复用既有合法编号 helper；生成包在准入/spawn 前调用同一消费校验；保留历史编号与既有合法格式。
- 验收：
  - [ ] 真实 fast-open 默认产物可直接被 admit → spawn 消费（无需人工改 id）
  - [ ] 正例 `#0001`、`role-12hex`、`role-b4` 通过；负例 `#12hex`、`#z1`、`#b2` 拒绝
  - [ ] 生产者与消费者使用同一夹具来源（不得各手写）

### 4.2 F25 — 只读空写集被传输层扩成读范围（P2）

- 问题：`write_set=[]` 被 `write_set or read_scope` 回填成读集合；底层 builder 又要求非空写列表，实际输出 `[SKILL.md]`，产生误导子智能体的宿主消息。
- 位置：`scripts/court_runtime.py:10316`–`10335`；`scripts/court_native_host_dispatch.py:110`、`248`。
- 修复：区分"字段缺失"与"字段明确为空"；在既有 contract 中表达合法只读任务；不得用读范围填写作集、不得删除写集绑定。
- 验收：
  - [ ] 空只读任务在 admission、native request、host message、office record 四处一致为空
  - [ ] 非空写任务正常；缺失字段负例按契约处理
  - [ ] 无"只读任务生成 `[SKILL.md]` 写提示"的路径

### 4.3 F26 — 公共 native selector 静默丢弃错误层级模型请求（P2）

- 问题：顶层 `model_request` 经 Namespace 投影后未知键消失，返回成功却不带 override；strict normalizer 本应报 `native_request_fields_invalid`。
- 位置：`scripts/court_runtime.py:12262`（Namespace）→ `10128`（四项身份投影）。
- 修复：公共边界先严格校验 raw keys，再做 Namespace 投影；保留"模型仅在正确 case-bound 层级选择"的约束。
- 验收：
  - [ ] 正确继承、合法显式选择均通过
  - [ ] 错误层级、未知参数被显式拒绝并提示正确字段
  - [ ] 无静默 PASS 路径

### 4.4 F23 — canonical 子智能体无法生成正式续派（P2）

- 问题：对既有 `native_host_identity_kind=canonical_agent_path` 的 target，续派构造器直接返回 `native_bridge:canonical_followup_issuer_unavailable`；宿主自有 `followup_task` 不能替代 Matrix capture/receipt 续派。
- 位置：`scripts/court_runtime.py:10347`；相关 `scripts/commands/court_native_bridge.py:241`–`282`。
- 修复：补齐 canonical target 的合法 host invocation / capture producer，接入既有 case、instance、直接上级、租约与 scope 校验；明确区分 fresh start 与已接纳 followup；禁止伪造 UUID、放宽身份校验或连续重 spawn 代替复用。
- 验收：
  - [ ] 真实当前宿主完成一次有界复用对照（含真实 host dispatch 与状态写入）
  - [ ] fresh start 与 followup 路径可区分
  - [ ] 失败的复用给出可执行诊断（而非通用拒绝）

### 4.5 F22 — 预载成功未转成实际业务（P1，链路收口）

- 问题（时间线）：三署 b4 ACK 均 PASSED/running，但差遣仍绑定 `Preload`、只读空写集；ACK 后使用不触发 idle 子智能体新 turn 的 `send_message`；另建业务 admission 返回 `allowed=false/runtime_capacity_exhausted`；首轮 90 分 58 秒无 A1–A7 业务成果。
- 根因：调用适配（trigger/压缩/唤醒工具）+ F23–F26 实现断点 + 测试与提示未约束"预载→第一项业务"整体路径。
- 修复：
  1. 初次 admission 即绑定真实有界业务 assignment / read_scope / write_set / expected result，预载作为其前置阶段；已有 Preload 差遣不得默默获得新写权限，业务变化走显式续派/范围更新。
  2. 业务 relay 由正确直接上级以可唤醒宿主的工具（`followup_task`）承载；**不要求 ACK / `preload_status` 作为前置**（用户 2026-10-05：ACK 限制优先废除，轻量替代见专项设计）。
  3. 容量拒绝或不支持续派时保留证据、给出下一步并停止无界重 spawn；不得移除安全、层级、身份与写集门禁换取表面进度（**ACK 前置除外**——按用户 2026-10-05 决策废除，见 §26.0）。
- 验收：
  - [ ] 真实有界任务读到首个业务文件并产生可核验结果，上级完成接受
  - [ ] 覆盖 child 已 idle、只读空写集、容量不足、业务范围变化四类场景

# 第三部分：跨版本机制

## 二十六、跨版本工程纪律

### 26.0 编排优先原则（用户 2026-10-05 拍板）

门禁（含 ACK、写集、容量等）不得被设计成"只允许单个写者 / 单个子智能体"的限制——这是**编排架构**，非必要限制应尽量抛弃：

- **保留（必要）**：直接上级层级、scope/write_set 冲突检测、容量事实、数据一致性类互斥（安装互斥/写锁等——属数据安全约束，非编排限制）、不默默扩权、不伪造身份；
- **放宽/抛弃（非必要）**：不得把"单实例只能承载一个业务""业务范围变化必须新 instance""同一 target 只能一个写者""容量拒绝后只能硬停""必须同一实例串行"当作硬门禁——改为**显式诊断 + 显式继续路径**（给出 `next_step`、计数可见、编排者在明确声明后可继续）；
- **ACK 限制（用户 2026-10-05 追加，优先废除）**：当前 ACK 类限制"完全起副作用"——**尽量放开**：凡"以 ACK/`preload_status` 为前提"的硬门禁（"未 ACK 不派业务"、reuse 候选强制 `preload_status=="PASSED"` 等）**默认废除**；**在允许的情况下直接删去 ACK 机制本身**（命令 / 字段 / 流程），不允许直接删除时**改良为诊断**（提示而非拒绝），不得新增对 ACK 的依赖。历史依据：最早 0.x 版本无 ACK 仍可用。ACK 机制以**轻量替代方案**替换（非简单删除）：用户明确其痛点是"太慢、治理过重、过于死板"，要求轻量替代且"工程化必要、不影响主要功能"——替代方案须满足：不阻塞主流程、无双层/多层校验、单一轻量信号或隐式完成 + 事后可追溯记录；由专项设计与实施（含既有检查与文档同步）。
- 若某处限制经论证必须保留，须在实施报告中给出**必要性论证**并单列受限项。
- **体积/规模预算（用户 2026-10-05 追加）**：体积类限制可**适度放宽**——入口预载预算（`ENTRY_PRELOAD_BUDGET_BYTES`，20 KiB）、便携源码预算（`references/manifests/source-state-budget.v1.json` 的 `portable_source.max_bytes/max_files`）、单文件行数预算（同 manifest 的 `source_lines`）；放宽须**最小必要**，并同步更新写死数值的检查与文档，在实施报告中单列「原值 → 新值｜理由｜影响面」。语义契约类限制（如白纸旨意/charter ≤2048 字符）与安全约束不在此列。

### 26.1 发布与 CI 验证（每版统一出口的组成部分）

- **触发条件**：本版验收通过后（出口清单全部达成；标 PARTIAL 的版本须经用户确认后才进入发布）；
- **发布动作**：推送到 GitHub、GitHub Release、npm 包发布（包版本号 = 本版号，dist-tag 按既有约定）；
- **CI 验证**：以既有 GitHub Actions 工作流执行验证；
- **CI 内容默认不改动**：不放宽门禁、不为过审修改检查集合；如某检查因平台/环境限制确实不可行，先提出方案、记录理由，经用户同意后才调整（优先"不改 CI"的其他解法）；
- **§26.0 豁免（避免与本节字面冲突）**：用户授权的机制替换（如 ACK 轻量替代）与预算放宽（§26.0）所引起的检查与文档变更，**不属于"为过审放宽"**；按 §26.0 记录（原值 → 新值｜理由｜影响面）并经用户确认后执行；
- **发布前核对与 publication_gates 判定**：`publication_gates` 为 **ref 级**门禁（仅列举的 ref 被 blocked，不是项目级禁发）。判定规则：本版发布所涉 ref 不在 blocked 列表 → 视为已解除、可发布；命中 blocked ref → 先报告，不强行发布（decretum-matrix 当前登记 `work/a02-baseline` 为 blocked，与本计划的 release 分支无直接关系；发布时以 `repo_control.py doctor` 的 `blocked_publication_refs` 输出为准）；
- **与根接受版本的关系**：发布（GitHub / npm）不自动推进 `workspace.yaml` 的 `version.current`；接受版本推进属根工作区治理动作，另行按用户指令执行（本计划不擅自改根工作区文件）；
- **证据**：Release 链接、npm 版本与 dist-tag、CI 运行回执与注释读取结果，记入本版执行记录与总纲执行记录。

### 26.2 其余纪律

1. 每版本统一出口：修复/实现 + 失败与成功对照（保留原始失败样本）+ 回归 + 文档同步 + 发布与 CI 验证 + 本文件执行记录。
2. 版本号连续占用：某版内容合并/推迟时后续顺延，不空号、不跳号。
3. Node 脱 Python 仅作为可评估方向：先纯协议/只读试点；Laya 保持独立 Python。
4. 治理收益用代表性真实任务度量；自报 95 分、checker PASS、未校准"完成度"不替代数据。
5. 不新造：第二套状态/身份/记忆框架、平行预载协议、完整 YAML 引擎、安装策略重写。
